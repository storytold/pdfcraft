# RFC: совместное редактирование PDF в PdfCraft

- Статус: Implemented, draft PR
- Автор: `pdfcraft/envoy` (по ADR-0001…0010 и `ARCHITECTURE.md`)
- ADR: `.craft/bus/decisions/0001-op-unit.md` … `0010-undo-offline.md`
- Upstream issue/PR: ветка `collab/impl`; PR открывается отдельно
- Реализация: `crates/collab-{proto,server,pdf,hub,client,client-pdf,session,ws}`,
  `apps/pdfcraft-collab-server`, UI за фичей `collab`
- Основание: `TASK.md`, `INTEGRATION.md`, `docs/collab/study.md`, `docs/collab/options.md`

## 1. Контекст

В PdfCraft нет совместной работы: один пользователь, один файл. Документ — граф
COS-объектов с copy-on-write оверлеем (`crates/cos/src/document.rs:36-80`);
единственная точка правки — `Session::apply(DocId, Edit)` (`crates/engine/src/session/editing.rs:22`).
`Edit` — внутренний enum на 106 вариантов, не serde, адресует страницы
индексами, аннотации — `(page, index)`; публичный API не отдаёт `ObjRef`.
Undo — глобальный снапшот всего документа (`crates/engine/src/history.rs:8,106`).
После каждой правки движок пишет incremental-ревизию и создаёт новый
`RenderPool` (`editing.rs:332,392`); на 100 000 страниц реинспекция ≈5 с
(`docs/gaps.md:315-317`).

Нужны два класса действий (TASK.md):

1. **merge** — комментарии/аннотации, ответы, статусы, значения полей формы;
2. **structural** — rotate/delete/insert/move/duplicate/replace страниц,
   закладки, структура полей.

## 2. Цели и не-цели

Цели:

- 2–5 участников на один PDF; комментарии и аннотации в реальном времени;
- структурные операции сериализованы сервером и не теряют страницы;
- роли `owner/editor/commenter/viewer`, проверка на сервере;
- per-user undo, reconnect, commit в кабинет;
- одиночный режим не ломается; фича за флагом.

Не-цели v1:

- зашифрованные и подписанные PDF (сессия запрещена);
- юридически значимая ЭП, OCR-очередь, мобильный touch;
- офлайн-редактирование structural-операций;
- CRDT/OT.

## 3. Модель данных для синхронизации

### 3.1 Единица операции (ADR-0001)

Wire-формат — не `Edit`, а нормализованная intent-операция:

```text
Op {
  op_id: string,          // UUID клиента, дедуп на сервере
  doc: DocKey,            // file id кабинета + версия файла
  base_version: u64,      // версия, на которой клиент строил операцию
  epoch: u64,             // PDF: меняется structural-операцией
  kind: command | primitive | structural,
  class: merge | structural,   // назначает адаптер, не клиент
  target: Target,
  payload: Value,         // схема операции; blob — по sha256
  preview: Option<string> // id локального оптимистичного результата
}
```

- `command` — нормализованная команда движка (без `Selection`);
- `primitive` — узкая операция (например, правка текста аннотации);
- `structural` — операция над страницами/деревом.

Реализованные действия v1: `annotation.add` (типизированная форма, см. §3.1.1),
`annotation.update` (итоговый стиль существующей аннотации, §3.1.2),
`annotation.font_size` и `annotation.info` (размер шрифта, автор, subject и
иконка заметки, §3.1.3), `annotation.set_contents`, `annotation.reply` (в том
числе ответ со статусом `/State`, §3.1.2), `annotation.delete`,
`annotation.restore`, `field.set_value`, `page.rotate`, `page.move`,
`page.delete`, `page.restore`, `page.insert`, `page.duplicate`
(`§3.1.4`) `page.replace`, `page.insert_blank`, `page.split`, `page.combine`
(`§3.1.5`). Остальные
правки в общей сессии отклоняются как `unsupported`, а не применяются только
локально.

#### 3.1.1 Схема `annotation.add`

Аннотация передаётся размеченным объектом `shape` (крейт `collab-annot`),
а не набором полей под каждый инструмент:

```json
{
  "action": "annotation.add",
  "nm": "ada-6f2a-1",
  "shape": {"kind": "text_markup", "markup": "highlight",
            "quads": [[20,200,120,200,20,190,120,190]]},
  "style": {"color": [0.1,0.7,0.3], "opacity": 0.4, "width": 1.0},
  "contents": "look here",
  "author": "ada"
}
```

- `shape.kind` ∈ `note`, `text_markup`, `rectangle`, `oval`, `line`, `ink`,
  `freehand_highlight`, `text_box`, `typewriter`, `stamp`, `mark`; `text_markup`
  несёт `markup` (highlight/underline/strike_out/squiggly) и `quads`, `line` —
  `from`/`to` и наконечники, `stamp` — палитровый `stamp` и `by`, `mark` —
  fill-and-sign знак.
- `style` — полный или частичный объект (`color`, `opacity`, `width`, `fill`,
  `border_color`, `border_shape`, `fill_opacity`, `text_opacity`); недостающие
  поля берутся из `Style::default_for(shape)`, поэтому минимальный payload
  рисуется одинаково на всех репликах.
- Клиент без `shape` (старый формат с `at`) читается как sticky note — совместимость
  на время раскатки.
- Не разделяются и отклоняются как `unsupported`: рисованные и печатные подписи,
  custom stamp (ссылается на XObject), redaction (структурная и необратимая),
  вложения. Это не «молчаливое понижение»: сервер отвечает ошибкой, клиент
  показывает причину и не применяет правку локально.
- Лимиты: ≤4096 quad, ≤1024 штрихов, ≤4096 точек на всё рисование (укладывается
  в 256 KiB сообщения), ≤64 KiB текста комментария.

Стиль уже существующей аннотации (цвет, прозрачность, толщина, наконечники
линий, заливка, граница) и ответы со статусом (`/State`) — отдельные операции,
§3.1.2; размер шрифта текста и свойства комментария (автор, subject, иконка
заметки) — §3.1.3.

#### 3.1.2 Стиль существующей аннотации и ответы со статусом

Правка внешнего вида уже существующей аннотации — одна операция
`annotation.update`, адресованная её `/NM`:

```json
{
  "action": "annotation.update",
  "style": {"color": [0,0,1], "opacity": 0.5, "width": 2.0,
            "fill": [0,1,0], "border_color": null, "border_shape": "oval"},
  "expect": {"color": [1,0,0]}
}
```

- `style` несёт **итоговый** вид; перечисленные поля меняются, отсутствующие —
  нет. `null` у `fill`/`border_color`/`border_shape` означает «убрать»
  (заливка, цвет или форма границы возвращаются к значению по умолчанию).
  Поддерживаются `color`, `opacity`, `width`, `endings`, `fill`,
  `border_color`, `border_shape`. `endings` — `/LE`: два имени для линии или
  полилинии, одно для callout'а (`"none"`, `"square"`, `"circle"`,
  `"diamond"`, `"open_arrow"`, `"closed_arrow"`, `"butt"`, `"r_open_arrow"`,
  `"r_closed_arrow"`, `"slash"`); имя вне списка, пустой список или число
  имён, которого у комментария нет (два у заметки, одно у callout'а),
  отклоняются как `invalid` до мутации.
- Почему одна операция, а не пять: интерфейс отправляет цвет, толщину,
  наконечники, заливку и границу одной правкой (один шаг undo), а сервер — одна
  версия, одна запись журнала. Движок применяет `Edit::RestyleAnnotation`
  (`pdfcraft_annot::restyle`) — «всё или ничего»: свойства проверяются до
  первой мутации, при сбое словарь аннотации (и её партнёров Replace Text)
  восстанавливается.
- Адрес проверяется **до** мутации: аннотации с таким `/NM` нет, она
  залочена, её внешний вид нельзя перерисовать или у неё нет запрошенного
  свойства (`width` у sticky note, `fill` у линии, `endings` у заметки или
  не то их число, `border_*` вне текстовых блоков) — операция отклоняется
  (`conflict`/`invalid`/`unsupported`), документ и версия не меняются.
- `expect` — CAS для undo: перечисленные поля должны всё ещё иметь указанные
  значения. Принятая операция несёт `style` и `before` (прежние значения тех
  же полей); undo — это `annotation.update` со `style = before` и
  `expect = style`. Если кто-то успел изменить те же поля, undo получает
  `conflict` (`retryable: false`) и чужой стиль остаётся.

Ответ комментария со статусом — это `annotation.reply` с полем `state`
(`none`/`accepted`/`rejected`/`cancelled`/`completed`):

```json
{"action": "annotation.reply", "nm": "bo-7f1-2", "author": "bo", "state": "accepted"}
```

- Родитель адресуется целью операции (`Target::Annotation`); его отсутствие —
  `conflict` до добавления чего-либо (удалённый родитель не воскресает
  ответом).
- Движок пишет статусный ответ сам (`/State`, `/StateModel /Review`,
  «Accepted set by bo»); реплика применяет его через
  `Edit::SetAnnotationStatusNamed` с `/NM`, назначенным клиентом, поэтому все
  реплики и журнал видят одну и ту же аннотацию и один и тот же текст.
- Статусный ответ удаляется и восстанавливается как обычный: копия удаления
  хранит тело с `state`, и `annotation.restore` возвращает ответ со статусом, а
  не простой комментарий.

#### 3.1.3 Размер шрифта и свойства комментария

Две правки «Comment Properties», которые не являются внешним видом, — тоже
атомарные операции, адресованные `/NM`. Разделены по движку: размер шрифта — это
`Edit::FontSizeAnnotation`, свойства — `Edit::SetAnnotationInfo`; у каждой свой
CAS и свой undo.

```json
{"action": "annotation.font_size", "size": 14.0, "expect": 10.0}
```

- `size` — итоговый размер в пунктах, 1–400 (движок перерисовывает текст и
  растит блок по переносам; меньше он не становится). `expect` — CAS: undo
  применяется, только пока у текста тот размер, который оставила операция.
- Принятая операция несёт `size` и `before` (число — прежний размер); undo —
  `annotation.font_size` со `size = before` и `expect = size`.
- Нечисловой размер, значение вне 1–400, залоченный комментарий и текст без
  `/DA` (заметка, линия, фигура) — `invalid`/`unsupported` до мутации; версия
  не двигается.

```json
{"action": "annotation.info", "info": {"author": "ada", "subject": "Review", "icon": "help"},
 "expect": {"author": "bo"}}
```

- `info` перечисляет **итоговые** значения; отсутствующее поле не меняется.
  Строка — новое значение (`/T`, `/Subj`), `null` — «убрать» (свойство
  удаляется, а не остаётся пустым), `icon` — имя иконки заметки (`comment`,
  `note`, `help`, … — все 14 стандартных). Пустая строка отклоняется
  (`invalid`): стереть имя случайно нельзя, только явным `null`.
- `icon` — только у sticky note (у остальных `invalid`); `author`/`subject`
  пишутся любому комментарию. Залоченный — `unsupported`.
- Принятая операция несёт `info` (то, что установлено) и `before` (прежние
  значения ровно тех полей, с `null` для отсутствовавших); undo — `info =
  before`, `expect = info`. Принятая операция применяется на репликах через
  `Edit::SetAnnotationInfo`, поэтому иконка перерисовывается один раз и
  одинаково.

Обе операции — `merge`-класс: они не двигают `epoch`, не требуют lease и
сливаются независимо от правок страниц; каждая — одна версия, одна запись
журнала и один шаг undo. Пакет «Comment Properties ▸ OK» интерфейс отправляет
как группу операций (`annotation.update` → `annotation.font_size` →
`annotation.info`), и группа отменяется одним шагом.

#### 3.1.4 Замена страницы и пустая страница

Две структурные правки, которые раньше не разделялись, — Replace Pages и
Insert Blank Page. Обе адресованы странице в текущем `epoch`, несут всё, что
нужно реплике, и поднимают `epoch` на единицу; операция с чужим `epoch` —
`stale` (retryable), документ при этом не меняется.

```json
{"action": "page.replace", "bytes": "<base64 одностраничного PDF>"}
```

- `Target::Page { index, epoch }` — заменяемая страница; её положение и число
  страниц не меняются. `bytes` — новая страница целиком (одностраничный PDF,
  base64), поэтому все реплики и журнал применяют одно и то же содержимое без
  второго канала.
- Payload проверяется целиком **до** мутации: base64, ровно одна страница,
  размер ≤ `MAX_RESTORE_PAGE_BYTES` (160 КиБ). Битая base64, ноль или две
  страницы — `invalid`; страница сверх бюджета — `limit`; отсутствующая
  страница — `invalid`, чужой `epoch` — `stale`. Ни один отказ не двигает
  `version`/`epoch`, не пишет журнал и не применяется локально.
- Адаптер снимает копию заменяемой страницы **до** правки (`page.copy`) и
  отвечает её токеном; принятая операция несёт `bytes` и этот токен. Undo —
  та же `page.replace` с `{"copy": "<токен>"}` и адресом страницы в новом
  `epoch`: страница возвращается точно (её содержимое — из копии сервера).
- Страница больше бюджета заменяется, но копия не снимается: undo, который
  называет копию (`{"copy": null}`), — `conflict` без изменения документа и
  версии. Redo повторяет исходную операцию (несёт `bytes`), поэтому не зависит
  от копии.

```json
{"action": "page.insert_blank", "width": 300.0, "height": 400.0}
```

- `Target::Page { index, epoch }` — позиция вставки (`index` может равняться
  числу страниц: вставка в конец). `width`/`height` — размер в пунктах
  (`> 0`, конечно, ≤ 14400 — 200 дюймов, предел размера страницы ISO 32000-2
  Annex C). Иное — `invalid` до мутации.
- Принятая операция несёт `at`, `width`, `height`; реплики строят ту же
  страницу через `Edit::InsertBlankPage`. Undo — `page.delete` по `at`.

#### 3.1.5 Разбиение и склейка страниц

Split/combine в движке — файловые операции (`Session::split`/`combine` дают
**новый** документ, `study.md` §6), поэтому в комнате они выражаются как
структурные правки над страницами того же документа: диапазон уходит из
документа вместе с частью в операции, а часть вставляется одной операцией.
Обе адресуются странице в текущем `epoch`, поднимают `epoch` на единицу,
требуют head-версию и lease; операция с чужим `epoch` — `stale` (retryable),
документ не меняется.

```json
{"action": "page.split", "count": 3}
```

- `Target::Page { index: from, epoch }` — первая страница уходящей части,
  `count` — сколько страниц уходит. Часть режет сервер из своего документа
  (`Session::extract`) и несёт её в принятой операции как `bytes` (base64,
  ≤ `MAX_RESTORE_PAGE_BYTES` = 160 КиБ), поэтому реплики и журнал могут вернуть
  её без второго канала. `bytes` от клиента игнорируются: иначе undo мог бы
  вставить в документ произвольное содержимое.
- Границы — самого документа: `count == 0`, `from + count` за последней
  страницей, `from`, который не является страницей, и `count`, равный числу
  страниц (разбиение не оставило бы документа), — `invalid`; часть сверх
  бюджета — `limit`. Ни один отказ не двигает `version`/`epoch`, не пишет
  журнал и не применяется локально.
- Принятая операция называет обе стороны: `from`, `to`, `count`, `kept`
  (сколько страниц осталось в документе) и `bytes`; результат добавляет
  `part: {sha256, len}`. Нумерация детерминирована: страницы до `from` не
  двигаются, страницы с `to` сдвигаются на `count` вниз, часть нумеруется со
  своей первой страницы.
- Undo — `page.combine` по `from` с частью из принятой операции: страницы
  возвращаются на прежнее место, документ — к исходному разбиению.

```json
{"action": "page.combine", "count": 2, "bytes": "<base64 PDF части>"}
```

- `Target::Page { index: at, epoch }` — позиция вставки (`at` может равняться
  числу страниц: вставка в конец). Часть едет целиком, поэтому все реплики
  вставляют одно и то же; `count` должен совпадать с числом страниц части, а
  файл — открываться, иначе `invalid` до мутации; часть сверх бюджета —
  `limit`. Принятая операция несёт `at`, `count` и `bytes` (для журнала и
  undo).
- Undo — `page.split` того же диапазона по `at`: документ возвращается к
  разбиению до склейки.

`page.combine` — форма Combine Files внутри комнаты: одна версия и один шаг
`epoch` на всю часть, тогда как `page.insert` вставляет по странице за
операцию. `page.split` — форма Split Document, которая **меняет** документ:
диапазон уходит, а не создаётся второй файл; выгрузить часть в файл — дело
клиента, у которого она есть в принятой операции.

В приложении это так и подключено (`ui-egui`, feature `collab`): Split в
сессии отправляет одну `page.split` по первой границе плана — страницы до неё
остаются (их номера и комментарии не двигаются), хвост уходит одной частью,
Undo — `page.combine` из принятой операции; диалог в этот момент называет
границу и число уходящих страниц, а не число файлов. Combine собирает часть
как обычно и отправляет одну `page.combine` в конец открытого документа.
Локальная выгрузка файлов остаётся только вне сессии.

### 3.2 Идентификаторы (ADR-0002)

| Сущность | Адрес на время сессии |
|---|---|
| страница | `page` + `epoch`; `epoch++` на каждую structural |
| аннотация | `/NM` (UUID, префикс `clientId`) + `page` + `epoch`; сервер отвергает дубли |
| ответ в thread | `/IRT` + `/NM` корня; сервер хранит карту |
| поле формы | полное имя `parent.child` |
| вложение | ключ name-tree |
| закладка | путь + `epoch` |
| слой | `ObjRef` OCG `(num, generation)` |

`ObjRef` страницы/аннотации — внутренний идентификатор сервера; на провод он не
попадает. Узкий API движка (`page_ref`, `annotation_ref`) реализован
(`de98b6e3`), но wire-формат от него не зависит.

`/NM` назначает клиент: `annotation.add`/`annotation.reply` несут поле `nm`,
сервер проверяет уникальность и сохраняет его (`Edit::AddAnnotationNamed`,
`Edit::ReplyToAnnotationNamed`). Если поле не передано, имя генерирует движок и
возвращает его в `applied.op.payload.nm`; клиент обязан применять именно его.

### 3.3 Документ на сервере

Авторитетная копия = `pdfcraft_engine::Session` с одним документом + журнал
операций + снапшоты (ADR-0005). Журнал хранит `opId`, `version`, `epoch`,
`actor`, `class`, адрес и payload; результат применения — не хранится, его
можно пересчитать.

## 4. Протокол

### 4.1 Транспорт

WebSocket/WSS, один набор сообщений для всех пяти приложений. JSON-фрейм
(текст), лимит одного сообщения — 256 KiB; blob-поля передаются отдельным
бинарным каналом или ссылкой `sha256`. Native-клиент: `tungstenite`;
web-клиент: `web-sys` WebSocket **или** host-мост `postMessage`
(`apps/pdfcraft-web/src/main.rs:120-160`) — выбирается в реализации, конверт
один.

Бинарный blob-канал в этой итерации не делается: решение 2026-11-09 — отдельный
PR после merge (STATUS §4). До него копия страницы едет base64 внутри операции и
ограничена 160 КиБ (`MAX_RESTORE_PAGE_BYTES`) — это принятое, проверенное
ограничение, а не временный обход; страница больше лимита отклоняется с
`limit` до изменения документа (§3.1.4–3.1.5).

### 4.2 Сообщения

| Тип | Направление | Поля | Семантика |
|---|---|---|---|
| `hello` | C→S | `v`, `app`, `doc`, `jwt`, `client` | JWT только здесь, не в URL |
| `welcome` | S→C | `sessionId`, `actorId`, `role`, `lease`, `version`, `epoch`, `limits` | сессия открыта |
| `op` | C→S | см. §3.1 | намерение |
| `applied` | S→C | `opId`, `version`, `epoch`, `actorId`, `op`, `result` | авторитетный результат; `op` — принятое намерение с нормализованным автором и `/NM`, по нему реплики применяют правку |
| `rejected` | S→C | `opId`, `code`, `retryable`, `hint{version,epoch}` | отказ |
| `presence` | C↔S | `page`, `viewport`, `cursor`, `selection`, `role`, `color` | эфемерно, ≤2 KiB, ≤10 Гц |
| `resync` | C→S | `lastVersion` | догон после разрыва |
| `snapshot` | S→C | `mode`, `cursor`, `bytes`/`ops` | база + хвост |
| `commit` / `commit-result` | C→S / S→C | см. §8 | сборка файла |
| `ping`/`pong` | C↔S | `ts` | heartbeat, продление lease |

Ошибки: `auth`, `lease`, `stale`, `conflict`, `forbidden`, `invalid`, `limit`,
`unsupported`, `busy`, `internal`. `busy` — «документ занят вызовом, который
сервер обязан закончить»: так отвечает второй коммит, пока публикация первого
ещё идёт (§8.2); он `retryable`, ничего не изменено.

### 4.3 Порядок и версии (ADR-0003)

- Один серверный монотонный `version` на документ; единственный порядок.
- `opId` дедуплицируется; окно последних операций персистентно (переживает
  рестарт) — повтор возвращает сохранённый `applied`, операция не применяется
  второй раз.
- `structural` требует `baseVersion == head`; иначе `rejected{code:"stale",
  retryable:true, hint:{version}}`.
- `merge` принимается на любой базе; при `epoch != head.epoch` —
  `rejected{code:"stale", retryable:true}`.
- Presence не увеличивает `version` и не журналируется.

### 4.4 Конфликты (ADR-0004)

| Ситуация | Политика | Что видит пользователь |
|---|---|---|
| два ответа в один thread | оба применяются, порядок серверный | оба ответа |
| правка текста/rect/цвета одной аннотации | LWW по свойству, побеждает серверный порядок | последнее значение + «изменено другим» |
| удаление аннотации с ответами | удаляются ответы и pop-up | thread исчез |
| ответ на удалённую аннотацию | `rejected{conflict}` | «комментарий удалён» |
| structural при активных участниках | эксклюзивно, `baseVersion == head` | «страницы изменены, обновите» |
| два structural одновременно | один применяется, второй stale | повтор после resync |
| значения полей | LWW по полному имени | последнее значение |
| структурная правка полей | только structural | «форма изменена» |

OT/CRDT не используются. LWW запрещён для содержимого (формулы, геометрия
страниц, текст документа) — только для свойств аннотаций и значений полей.

### 4.5 Reconnect и догон

Клиент присылает `lastVersion`. Если хвост журнала начиная с `lastVersion+1`
в окне — сервер отдаёт `applied`-последовательность; иначе `snapshot`
(база + хвост) и клиент сбрасывает непринятую очередь. Клиентские ops с
`opId`, уже применёнными, не повторяются (дедуп).

### 4.6 Снапшоты и compaction (ADR-0005)

- База — рабочие байты PDF (`Session::save_bytes`), хвост — журнал операций.
- Периодический snapshot: `write_incremental` от текущей базы; compaction по
  N операций / M байт / T минут сводит журнал в новую базу (допустим full
  rewrite только на компакции). Реализованы все три порога
  (`RoomConfig::forced_commit_ops` / `forced_commit_bytes` /
  `forced_commit_idle_secs`, STATUS §4, §6.1): первые два считаются от
  последней базы, третий — «idle» журнала: с момента последней принятой
  операции прошло T (по умолчанию 300 с, `0` выключает). Idle — состояние
  комнаты, а не соединения: reconnect его не сбрасывает, и после рестарта он
  восстанавливается по времени записи в журнале (`ms` в `JournalRecord`).
  Комнату с уже записанной, но не опубликованной базой (журнал пуст) порог по
  времени не трогает — её публикует следующий коммит/вход/уход или очередь
  публикаций.
- Хранится 1–2 базы + хвост; TTL сессии — по правилу кабинета.
- Per-user undo-журнал хранится отдельно и в снапшот не входит.

## 5. Presence (ADR-0006)

Отдельный тип в том же WS; не журналируется. Полезная нагрузка: `page`
(индекс + epoch), `viewport {x,y,zoom}`, `cursor` (user space), `selection`
(`/NM` или rect), `role`, `color`. Частота ≤10 Гц, размер ≤2 KiB, при
backpressure — drop-stale, TTL 30 с. На wasm рендер идёт в UI-потоке
(`crates/render/src/raster/pool.rs:261-283`), поэтому presence не должен
вызывать перерисовку страницы.

`selection` — геометрия или имя, без содержимого документа: выбранный
комментарий (`{kind:"annotation", nm}`) или прямоугольник в user space
(`{kind:"text", page, rect}`) — им передаётся и диапазон текста (его bounding
box), и column-select. Текст выделения, `Contents` комментария и токен в
presence не попадают; смена выделения не создаёт операцию, не меняет `version`
и не журналируется (§4.3).

Реализация (UI `crates/ui-egui/src/collab.rs`, `crates/ui-egui/src/canvas.rs`):

- курсор берётся из `DocView.local_cursor` — точку над страницей разрешает
  страничный модуль через `PagePointer`, приложение не читает указатель egui;
- отправка коалесцируется: не чаще 100 мс, только при изменении (страница,
  epoch, точка, зум, роль) и раз в 1 с как heartbeat, чтобы читатель не
  выглядел «неактивным»;
- чужой курсор рисуется стрелкой и именем в цвете участника на его странице;
  presence с чужим `epoch` не рисуется (индекс страницы уже не тот);
- выделение берётся из состояния страницы: выбранный комментарий — его `/NM`,
  выбранный текст — bounding box квадов в user space; своё выделение в presence
  не рисуется как чужое (его рисует сам редактор), а viewer получает и рисует
  выделения остальных, хотя операций не пишет;
- TTL общий для курсора и выделения: presence не журналируется и не
  переигрывается, поэтому запись старше 30 с показывается «inactive», её курсор
  и выделение не рисуются; `leave` и разрыв сокета убирают участника сразу.

## 6. Undo/redo на пользователя (ADR-0010)

- Undo — обычная операция с `baseVersion = head`, но с `inverse`-payload.
- Undo compare-and-set: inverse называет значение, которое оставил отменяемый
  op (`expect`), и сервер применяет его, только если текущее значение всё ещё
  это; иначе `rejected{conflict}` без молчаливой перезаписи. Так закрыт
  сценарий «моя правка перекрыта чужой, undo вернул чужое значение». CAS
  действует для текста комментария, значения поля, угла поворота и (через
  `baseVersion == head`) для структурных операций.
- Для аннотаций inverse: удалить созданное, восстановить прежние `Contents`,
  `State`, `Color` из inverse-журнала клиента.
- Удаление: сервер хранит копию удалённого (RFC §6.1) и отвечает её токеном в
  `applied.op.payload.copy`; inverse — новая операция `annotation.restore` или
  `page.restore`, которая называет токен. Клиент не может построить inverse
  удаления сам: содержимого у него уже нет.
- Undo не откатывает чужие правки: он применяется поверх head и получает
  новую `version`; при конфликте — `rejected{conflict}`. Inverse — обычная
  операция: клиент ставит её в очередь как любую свою правку, поэтому
  `baseVersion` и `epoch` адреса берутся из head на момент отправки (иначе undo
  поворота всегда был бы stale: inverse строится на epoch до операции).
- Inverse поворота — противоположный поворот (`degrees` в `RotatePages` — это
  дельта, а не угол), с `expect` = угол, который операция оставила.
- Стек undo — на актора, на сессию; TTL истории — по TTL сессии.
- Offline: только `merge`-операции с `opId`; structural offline запрещены.

### 6.1 Серверные копии удалённого

- `annotation.delete` кладёт в комнату проводное тело комментария (то, что
  пришло в `annotation.add`/`annotation.reply`, с его `/NM`) и `/IRT`
  родителя. `annotation.restore` с токеном добавляет тело обратно тем же
  `/NM` (`AddAnnotationNamed`), ответ — reply — снова reply
  (`ReplyToAnnotationNamed`). Принятая операция несёт тело (`payload.body`),
  поэтому её применяют все реплики и повторяет журнал.
- `page.delete` снимает одностраничный PDF страницы **до** удаления.
  `page.restore` вставляет его `InsertPagesFrom` по прежнему индексу; операция
  несёт страницу в `payload.bytes` (base64), чтобы обойтись без второго канала.
- `page.insert` и `page.duplicate` устроены так же: операция несёт
  одностраничный PDF (`payload.bytes`) и позицию (`payload.at`), адрес —
  `Target::Page` в текущем epoch (`page.insert` — позиция вставки, `index` может
  равняться числу страниц; `page.duplicate` — исходная страница, копия идёт на
  `at`). Обе поднимают epoch, поэтому операция с чужим epoch — `stale`
  (retryable). Undo вставки — `page.delete` по `at`. Страница больше
  `MAX_RESTORE_PAGE_BYTES` отклоняется как `limit` **до** изменения документа и
  локально не применяется.
- `page.replace` (RFC §3.1.4) снимает копию заменяемой страницы **до** правки и
  отвечает её токеном в `applied.result.copy`; принятая операция несёт `bytes`
  (чтобы репликам и журналу не нужна была копия) и токен. Undo —
  `page.replace` с `payload.copy`: адаптер берёт страницу из копии, снова
  пишет в принятую операцию `bytes` и снимает копию того, что заменил, — так
  undo сам отменяем. Копии нет (страница была больше бюджета) — undo с
  `"copy": null` отклоняется как `conflict` до мутации. `page.insert_blank`
  несёт размер страницы (`width`/`height`, пункты) и позицию (`at`), поэтому
  реплики строят ту же пустую страницу; его undo — `page.delete` по `at`.
- Копии живут в памяти адаптера, ограничены (64 копии / 64 МиБ, старые
  вытесняются) и не пишутся на диск: `replay` заново применяет удаления в
  порядке журнала и восстанавливает те же токены. Нет копии — нет undo:
  `annotation.delete` без тела (комментарий пришёл из файла, а не из комнаты)
  и страница больше бюджета кадра удаляются без токена, и undo честно
  отказывает.
- Предел страницы — `MAX_RESTORE_PAGE_BYTES` (160 КиБ): base64 внутри кадра
  256 KiB. Больше — копия не снимается (RFC §16).

## 7. Роли и права (ADR-0008)

JWT в `hello`: `{sub, doc, role, sid, exp}`; `role ∈ owner|editor|commenter|viewer`.
Проверка на сервере для каждой операции:

- `viewer` — только presence/snapshot;
- `commenter` — merge-операции аннотаций/полей, без structural и без
  `Edit::Protect/ApplyRedactions/Sanitize`;
- `editor` — всё, кроме управления сессией;
- `owner` — всё + закрытие сессии.

Дополнительно проверяются PDF-permissions (`crates/engine/src/edit/run.rs:9-140`).
Токен не логируется; `Origin` проверяется для web.

**Lease — liveness одного писателя, а не право записи.** Право записи даёт
только роль (ADR-0008 §2–3); lease отвечает на другой вопрос — жив ли
писатель, который сейчас держит эксклюзивный structural-поток:

- одна комната на файл, один writer-lease (owner/editor); `commenter`/`viewer`
  lease не получают и структурных операций всё равно не делают;
- lease имеет TTL (по умолчанию 120 с) и продлевается `ping` (heartbeat раз
  в 30 с); разрыв WS освобождает его сразу;
- потеря/занятость lease → `rejected{code:"lease", retryable:true}` — клиент
  ждёт и повторяет, это не отказ в правах;
- истечение lease по TTL, а не блокировка комнаты: пока писатель жив, второй
  editor входит с `ttl_secs = 0`, комментирует и получает `lease` только на
  структурной операции.

Эта формулировка — общая с DeckCraft (§7 их RFC) и CADCraft (ADR-0008):
различаются только транспорт и TTL, не смысл.

## 8. Commit и версии (ADR-0009)

- Commit инициирует owner/editor или сервер по TTL/выходу последнего.
- Сервер применяет журнал к своей базе и пишет файл: `save_bytes`
  (incremental) по умолчанию; `save_full_bytes` только если операция требует
  полного rewrite (delete pages, redaction, PDF/A, смена шифрования).
  `/ModDate` инжектируется (`Session::with_clock`) — commit детерминирован.
- Кабинет получает `{fileId, bytes, sha256, version, expectedVersion}` и
  создаёт новую версию; исходная сохраняется.
- Внешнее изменение файла (etag/`file_watch`) → `409`, сессия не
  перезаписывает; кабинет предлагает «сохранить копию».
- После commit сессия жива, `dirty=false`, `version` не сбрасывается.

### 8.1 Долговечность журнала

Комната хранит на диске (`<data>/<fileId>/`):

```
CURRENT                 {"version":N,"epoch":E} — какую базу грузить
versions/<N>/file.pdf   документ на версии N
journal.jsonl           {"version":N,"actor":"…","op":{…}} на каждую принятую операцию
```

- Операция сначала добавляется в `journal.jsonl` и синхронизируется
  (`sync_data`), и только потом клиенту уходит `applied`. Падение сервера
  теряет максимум необработанную операцию, но не подтверждённую.
- Commit: пишет новую базу `versions/<N>/file.pdf` (fsync + rename), затем
  атомарно заменяет `CURRENT`, затем выкидывает из журнала записи с
  `version <= N`. Падение между базой и `CURRENT` оставляет старую базу и
  полный журнал; падение после `CURRENT` оставляет устаревшие записи, которые
  при replay пропускаются по версии. Двойного применения нет ни в одном окне.
- Старт: читается `CURRENT`, открывается база, записи с
  `version > CURRENT` прогоняются через `Room::replay` — это **уже принятые
  записи**, поэтому членство, роль, lease и дедупликация при replay не
  проверяются повторно (иначе история бы отваливалась: lease после рестарта
  другой). `epoch` восстанавливается из `CURRENT` и структурных операций, так
  что повторы уже принятых merge-операций ложатся в тот же epoch, в котором
  были приняты.
- Живой клиент с устаревшим `epoch` получает `rejected{code:"stale",
  retryable:true}` на merge-операцию (§4.3) и обязан сделать `resync`;
  применяется только то, что пришло в ответе. Replay не меняет это правило:
  он про журнал, а не про текущий клиент.
- Сбой записи журнала после того, как адаптер уже изменил документ, отравляет
  комнату (`ErrorCode::Internal`, все записи отклоняются, комната видна в
  `/health` и `/metrics` как `read_only`); commit при этом разрешён и спасает
  состояние.
- Базы старше той, на которую указывает `CURRENT`, удаляются после переезда
  маркера: на диске одна база и журнал, а не PDF на каждый commit. Версии
  хранит кабинет.
- Порванная последняя строка журнала (частичная запись) игнорируется: её
  никто не подтверждал. Порванная строка в середине — ошибка старта, а не
  тихая потеря.

### 8.2 Контракт с кабинетом

Control-plane включается флагом `--control ADDR` (отдельный loopback-порт;
без флага его нет). `POST /v1/sessions` создаёт комнату или возобновляет её:

```json
{"fileId":"file-123","jwt":"<RS256>","etag":"sha256:…",
 "bytes":"<base64 PDF>"}
```

вместо `bytes` допустим `"url": "http://…"`. Ответ `201` (комната создана)
или `200` (возобновлена): `{"fileId","version","epoch","etag","created"}`.

- JWT проверяется тем же верификатором, что и `hello` (`401` при неверной
  подписи или сроке, `403` если токен выписан на другой `fileId`). Роль токена
  не ограничивает запуск комнаты: операции всё равно проверяет комната.
- `fileId` — только `[A-Za-z0-9._-]`, 1–128 байт: он становится именем
  каталога в `--data`.
- `etag` — `sha256:<hex>` содержимого файла. Если он передан, он обязан
  совпадать с хешем присланных байтов (`400`) и с тем, что держит комната
  (`409`, в теле — `etag` и `version` комнаты). `409` — это «файл изменился
  вне сессии»: сессия поверх чужой версии не начинается.
- Источник — inline `bytes` (base64) или `url` (только `http://`: TLS
  терминируется прокси). Файл обязан начинаться с `%PDF-`, размер ограничен
  `--max-source-bytes` (256 МиБ).
- `--documents` остаётся **dev-режимом** (комнаты из каталога, без кабинета);
  прод-путь — control-plane.

Общий контракт пяти редакторов (общая архитектура кабинета, разделы 4.1 и
5.2) описывает тот же вызов иначе: `Authorization: Bearer <service token>`, тело
`{fileId, app, owner, roles, initialName, initialBytes?}` и ответ
`{sessionId, wsUrl, expiresAt}`; callback —
`POST /api/v1/internal/office/sessions/{sessionId}/commit` с
`{fileId, name, bytes, expectedVersion?}` и ответом `{version, etag}`. Общий
документ сам называет имена предложением, финальные фиксирует RFC проекта.
PdfCraft v1: `jwt` в теле (тот же токен, что уходит в `hello`; сервисного
токена у демона нет, `POST /v1/sessions` и `/resolve` принимают тот же JWT в
`Authorization: Bearer`), `bytes`/`initialBytes` и `url` как источник, `etag` =
`sha256` байтов. Версии: комната нумерует коммиты сама, а номер копии в
кабинете берётся из ответа callback, когда он его называет
(`{version, etag}`); без тела — `expectedVersion + 1`. Так расходятся две
нумерации только после разрешения конфликта (§8.2), и обе хранятся в маркере
`CABINET`. Кабинет, который отвечает своим номером, адаптера не требует;
кабинет без `{version}` считается инкрементным по одному на публикацию.

**Commit-callback** (`--callback-url`; токен — env
`PDFCRAFT_COLLAB_CALLBACK_TOKEN`, заголовок `Authorization: Bearer`):

```json
{"fileId":"file-123","bytes":"<base64 PDF>","sha256":"…",
 "version":7,"expectedVersion":6,
 "idempotencyKey":"file-123:7:…"}
```

- `idempotencyKey` = `fileId:version:sha256` и то же значение в заголовке
  `Idempotency-Key`. Он называет полезную нагрузку, а не попытку: повтор того
  же коммита приходит с тем же ключом, и кабинет, который уже принял байты, но
  не успел ответить, узнаёт дубль. Версия одна, второй не создаётся. Ключ
  выводится, а не генерируется, поэтому повтор после рестарта демона (база
  записана, но не опубликована) приходит с тем же ключом.
- `2xx` — кабинет принял версию. Тело ответа `{version, etag}` (общий контракт)
  задаёт копию кабинета: `version` — `expectedVersion` следующего коммита,
  `etag` — маркер. Пустое или нечитаемое тело — `expectedVersion + 1` и
  `sha256:<hex>` опубликованных байтов.
- `409` — у кабинета другая версия: коммит отклонён, комната помечается
  `conflict` (`/health`, `/metrics`), правки продолжают приниматься и
  журналироваться, **очередь публикаций останавливается** до переиздания
  комнаты: повторять тот же `expectedVersion` бессмысленно.
- Сеть, `429` и `5xx` — комната остаётся `publishing`, и фоновая очередь
  демона повторяет **ту же** публикацию (тот же `version`, `expectedVersion`,
  `sha256` и ключ) с удваивающейся паузой: 1 с, 2 с, 4 с … до 60 с
  (`collab-ws::Config::publication_backoff` / `publication_backoff_max`,
  тик очереди 100 мс). Ждать следующего коммита или ухода последнего участника
  не нужно. Пока публикация в очереди, комната `publishing`, поэтому новый
  коммит этого документа получает `busy` (`retryable`): более новая база не
  может обогнать очередь. Успешный повтор двигает `committed_version` и
  отпускает комнату; если за время очереди пришли правки, а участников нет,
  транспорт публикует и эту базу.
- Другой `4xx` — ошибка контракта, повтор её не исправит: база записана
  локально, но версия не опубликована, комната остаётся `dirty`, следующий
  коммит повторит публикацию.
- `/metrics` отдаёт `pdfcraft_collab_publication_retries_total` — число
  фоновых попыток с момента старта процесса.
- Публикация идёт **вне блокировки hub**: под локом пишется база и снимается
  снимок для отправки (`Room::commit` → `Commit`), лок отпускается, затем
  выполняется HTTP-вызов (`Commit::publish`), затем под локом записывается
  результат (`Room::finish`). Недоступный кабинет задерживает соединение
  коммитящего, а не другие документы. Пока публикация идёт, второй коммит
  этого документа получает `busy` (`retryable`): две версии не могут уйти в
  кабинет не по порядку. Тот же путь у коммита по уходу последнего участника;
  серверные компакции (лимит 10) идут через ту же очередь.
- Очередь живёт в процессе: рестарт демона её теряет. База на диске при этом
  остаётся неопубликованной, комната после рестарта `dirty`, и публикацию
  повторит следующий коммит, вход участника или уход последнего — с тем же
  выведенным ключом, поэтому это по-прежнему дубль для кабинета, а не вторая
  версия.

**Внешнее изменение файла.** Маркер `--data/<fileId>/CABINET`
(`{"version":N,"etag":"…","expected":M}`) хранит, что кабинет имеет; он
пишется атомарно и может отставать от базы — ровно на непубликованные правки.
`version` — версия комнаты у опубликованной базы (проверка «есть
несохранённое» после рестарта), `expected` — номер той же копии в нумерации
кабинета: его комната отправляет как `expectedVersion`. До первого разрешения
конфликта они совпадают; маркер без `expected` читается как
`expected = version`. Проверка:

- dev-режим: `sha256` файла `--documents/<fileId>.pdf` сверяется с маркером
  перед каждым коммитом; замена файла → `Conflict`, база не пишется;
- control-plane: etag сверяется при `POST /v1/sessions` (и сервером, и
  кабинетом по `expectedVersion` в callback).

**Разрешение `conflict`.** `409` останавливает очередь публикаций, и повторять
тот же `expectedVersion` бессмысленно, поэтому выход — явный вызов оператора:

```text
POST /v1/sessions/{fileId}/resolve
Authorization: Bearer <service token>
{ "expectedVersion": 7, "etag": "sha256:…" }
→ 200 { "fileId", "version", "epoch", "etag", "cabinetVersion", "conflict": false }
```

- Токен — тот же RS256 JWT кабинета; `fileId` обязан совпадать с путём, роль —
  `owner`/`editor`. Ответ `401`/`403`.
- `expectedVersion` — версия копии в кабинете и `etag` — её etag. Версия
  обязана быть **новее** той, что комната уже знает (`400` иначе): иначе
  следующий коммит получит тот же `409`. Комнаты нет — `404`; комната не в
  конфликте (в т.ч. повторный resolve) — `409 not_conflict`; идёт публикация
  — `409 busy`. Любой отказ ничего не меняет.
- Успех снимает флаг (`/health`, `/metrics`), записывает маркер кабинета
  (`expected = expectedVersion`, etag) и оставляет комнату `dirty`:
  неопубликованная работа ждёт в журнале, следующий коммит (кнопка, уход
  последнего, серверная компакция) уходит с этим `expectedVersion`. Ответ
  кабинета `{version, etag}` на этот коммит становится маркером, т.е.
  разрешение действует до конца сессии, а не на один коммит.
- Успех считается в `pdfcraft_collab_conflicts_resolved_total`.

Эксплуатация и полный список кодов — [`server.md`](server.md).

## 9. Сервер

- `pdfcraft-collab-server` — отдельный native-бинарь (не режим приложения).
- Зависимости: `pdfcraft-engine` (headless, без egui), `pdfcraft-collab-proto`,
  WebSocket-стек, JWT, storage. Лицензии — по allowlist upstream.
- Комната = `(fileId, app)`; воркер на комнату; падение комнаты не роняет
  чужие.
- Healthcheck, метрики (сессии, ops/s, размер журнала, lag), лимиты
  (участники, сообщение, ops/s, размер документа), TTL.
- Логи без содержимого PDF, комментариев и токенов.
- Порты: `--listen` (WebSocket), `--health` (health/metrics, без авторизации —
  probes), `--control` (control-plane `POST /v1/sessions` и
  `POST /v1/sessions/{fileId}/resolve`, JWT обязателен; без флага выключен).
- Состояние комнаты `--data/<fileId>/`: `CURRENT` (версия и epoch базы),
  `versions/<N>/file.pdf`, `journal.jsonl`, `CABINET` (версия комнаты, версия
  кабинета и etag копии, §8.2). Базы старше `CURRENT` удаляются на коммите; версии хранит
  кабинет.
- Коммит идёт по одному пути для кнопки и для ухода последнего участника:
  сначала база локально, затем callback кабинету. Callback — с таймаутом и
  **вне** блокировки hub: под локом база и снимок, HTTP после снятия, результат
  под локом (§8.2).
- Control-plane HTTP — свой минимальный разбор запроса: `Content-Length`,
  ограничение тела, без chunked/keep-alive. Отказ говорит кодом и текстом,
  тело ответа — JSON `{"code","message"}` (+ `etag`/`version` при `409`).

## 10. Клиент

- Feature flag `collab` (default off), включается кабинетом через
  `pdfcraft:session` (host-мост) или query-параметр `collab=1`.
- Интеграция: `Session` остаётся источником истины для локального применения;
  collab-слой добавляет `apply_remote(op)` и отдельный путь применения чужих
  операций мимо `push_undo` (`editing.rs:188`).
- UI: список участников, курсоры/выделения, индикатор синхронизации; viewer и
  commenter не видят запрещённых команд (и сервер их отвергает).
- Одиночный режим: те же `save_bytes`, `render`, undo; collab не влияет.

## 11. Тесты

Headless, без GUI, 2–3 клиента:

1. unit: сериализация конверта, дедуп `opId`, `baseVersion`/`epoch`.
2. два клиента комментируют разные страницы — оба комментария видны.
3. два ответа в один thread — оба сохраняются, порядок стабилен.
4. правка/удаление одной аннотации — LWW и каскад ответов.
5. два structural одновременно — один stale, после resync применяется.
6. structural + merge на одной странице — merge отклоняется по epoch.
7. reconnect: `lastVersion` в окне и вне окна (snapshot).
8. роли: viewer/commenter не могут structural; сервер отвергает.
9. формы: значения полей LWW, структура — только structural.
10. undo: отмена своей правки не откатывает чужую; undo после удаления
    комментария и страницы возвращает содержимое из серверной копии на обеих
    репликах; undo поверх чужой правки — `conflict` (CAS).
11. presence: 10 Гц, коалесцирование, чужой `epoch` не рисуется, TTL 30 с
    делает участника «inactive».
12. commit: `.pdf` открывается в Chrome/Adobe; ссылки, закладки, формы,
    вложения целы; исходная версия сохранена.
13. большой PDF (500+ страниц) и 100k страниц — бюджет применения.

## 12. Безопасность

- JWT только в `hello`; не в URL, не в логах.
- `Origin` для web; WSS; размер сообщения и число ops/s ограничены.
- Сервер не логирует `Contents`, `T`, `payload` аннотаций, байты PDF.
- Server-side проверка роли и PDF-permissions; не полагаться на UI.
- Зашифрованные и подписанные PDF — сессия запрещена в v1.

## 15. Запуск сервера

```bash
cargo run -p pdfcraft-collab-daemon --release -- \
  --data /srv/collab/data \
  --jwt-key /srv/collab/cabinet-public.pem --jwt-audience lzmkm \
  --listen 127.0.0.1:8787 --health 127.0.0.1:8788 \
  --control 127.0.0.1:8789 \
  --callback-url http://cabinet.internal/v1/collab/commit \
  [--max-source-bytes N] [--origin https://cabinet.example] [--app pdfcraft]
```

- прод: `POST /v1/sessions` заводит комнату (bytes или url, JWT, etag);
  callback-токен — `PDFCRAFT_COLLAB_CALLBACK_TOKEN`;
- dev: `--documents /srv/collab/documents` открывает по комнате на
  `<fileId>.pdf` и не даёт коммитить поверх изменённого файла;
- commit (кнопка, или последний участник ушёл при непустой сессии) пишет базу
  в `--data/<fileId>/` атомарно, затем публикует её в кабинет; исходный файл в
  `--documents` не меняется;
- `/health` → `{"ok":true,"rooms":N,"clients":M,"poisoned":[],"conflict":[]}`;
  `/metrics` — Prometheus-текст (`pdfcraft_collab_room_conflict{room=…} 1` для
  комнат, которым отказано в коммите);
- логи не содержат токенов, текста комментариев и байтов PDF.

## 16. Известные ограничения (до prod)

Операционный статус, тестовая матрица и план следующей сессии —
[`STATUS.md`](STATUS.md).

1. ~~Журнал операций не переживает рестарт~~ — журнал и версионированные базы
   лежат на диске (§8.1); восстановление с базой и replay хвоста проверено
   тестами `a_room_replays_its_journal_after_a_restart` и
   `a_restart_recovers_the_last_commit`.
2. ~~Web-клиент к серверу не подключён~~ — в `collab-session` один драйвер
   протокола за трейтом `Transport` с двумя реализациями (нативный воркер и
   браузерный `web-sys` WebSocket), UI держит `Box<dyn Sink>` вместо нативного
   `Handle`, host-мост `pdfcraft:session`/`session-state`/`presence`/`commit`/
   `committed` реализован (STATUS §4, §6.3). Не проверено: прогон в браузере
   против страницы кабинета (нужны `craft-web-host` из craft-libs и страница,
   которая говорит этот контракт).
3. ~~Presence: панель участников и страница/зум; курсоры и выделения не
   рисуются~~ — курсор над страницей отправляется (≤10 Гц, коалесцирование,
   TTL 30 с) и рисуется у остальных цветом участника; выделение (`selection`)
   отправляется как `/NM` выбранного комментария или прямоугольник в user space
   (диапазон текста — его bounding box) и рисуется у остальных тем же TTL;
   смена выделения не создаёт операцию и не меняет `version` (STATUS §4,
   §5 п.4). Не делятся: несколько выбранных комментариев (только основной),
   по-строчная геометрия диапазона (один прямоугольник) и каретка ввода.
4. ~~Удаление аннотации/страницы не отменяется~~ — серверные копии и
   `annotation.restore`/`page.restore` (RFC §6.1). Остаются границы:
   комментарий, пришедший из файла (не из комнаты), удаляется без копии и не
   отменяется; страница больше 160 КиБ не отменяется (нет кадра), а замена
   такой страницы применяется, но без копии — её undo отклоняется как
   `conflict` (§3.1.4); часть разбиения больше 160 КиБ не уходит из документа
   вовсе (`limit`, §3.1.5), поэтому «отменить нечем» здесь не возникает;
   копии
   старше 64 удалений вытесняются; undo текста/поля/поворота — CAS (RFC §6).
5. ~~Не разделяются произвольные аннотации~~ — типизированный payload
   (`collab-annot`) разделяет `TextMarkup`, `Rectangle`, `Oval`, `Line`, `Ink`,
   `FreehandHighlight`, `TextBox`, `Typewriter`, `Stamp`, `Mark` и `Note`
   (RFC §3.1.1), правку стиля существующей аннотации (включая наконечники
   `/LE`) и ответы со статусом (§3.1.2), размер шрифта и свойства комментария
   (§3.1.3); не разделяются подписи, custom stamp, redaction и вложения. Из
   структурных операций разделяются insert/duplicate/delete/move/rotate/
   replace/blank insert (§3.1.4) и split/combine (§3.1.5); не разделяется
   правка содержимого страницы.
6. ~~Комнаты заводятся каталогом файлов; control-plane не реализован~~ —
   `POST /v1/sessions`, callback коммита, идемпотентный повтор публикации и
   `409` при внешнем изменении реализованы (§8.2); `--documents` остался
   dev-режимом. Фоновая очередь демона повторяет неудачный callback с
   удваивающейся паузой и ключом `fileId:version:sha256`, не дожидаясь
   следующего коммита; `409` останавливает очередь. Выход из `conflict` —
   явный `POST /v1/sessions/{fileId}/resolve` с версией и etag кабинета
   (§8.2): флаг снимается, следующий коммит публикуется с этой версией, а ответ
   кабинета задаёт ожидание следующего, так что разрешение не одноразовое
   (`pdfcraft_collab_conflicts_resolved_total`); повторный resolve без
   конфликта отклоняется. До prod остаётся: очередь живёт в процессе (рестарт
   теряет её, публикацию повторяет следующий коммит/вход/уход) и приём
   `https://` без прокси.
7. ~~Нет WSS/TLS termination внутри сервера~~ — ожидается reverse proxy; это
   ограничение распространяется и на control-plane, и на callback: оба говорят
   только по `http://`, `https://` отклоняется явной ошибкой.
8. Headless-применение без пересборки view: `apply_remote` обновляет
   `RenderPool` на каждую правку, батча на окно commit нет.
