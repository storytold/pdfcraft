# Options: протокол совместного редактирования для PdfCraft

> Артефакт Phase 0 к `study.md`. Три варианта различаются **механизмом**
> синхронизации, а не настройками. Рекомендация — вариант B.

- Проект: `pdfcraft`
- Коммит: `f42fda734243b66f54db87923d7c981d5221419e`
- Дата: 2026-11-06
- Автор: `pdfcraft/envoy`

## Требования, из которых выбран вариант

Из `TASK.md` и `INTEGRATION.md` проекта:

1. Один PDF, 2–5 участников, 100+ страниц; документ целиком на каждое
   нажатие не отправляется.
2. Два класса действий: аннотации/комментарии/формы мержатся; структурные
   операции страниц (rotate/delete/insert/move/split/combine) сериализуются
   сервером.
3. Роли `owner/editor/commenter/viewer`, проверка на сервере.
4. Per-user undo; отмена не откатывает чужие правки.
5. Reconnect и догон; идемпотентность.
6. Commit отдаёт валидный `.pdf`; исходная версия сохраняется; внешнее
   изменение → `409`.
7. Не ломать round-trip: ссылки, закладки, метки, формы, слои, вложения,
   шифрование, подписи.
8. Rust/WASM, без тяжёлого CRDT-стека; headless-тесты без GUI.

Факты из `study.md`, которые отсекают варианты:

- `Edit` — 106 вариантов, **не сериализуем**, часть несёт `Arc<Vec<u8>>`,
  адресация позиционная (`crates/engine/src/edit.rs:21`).
- Публичный API не отдаёт `ObjRef`; `/NM` не уникален
  (`crates/render/src/inspect/model.rs:304-330`,
  `crates/automation/src/comments.rs:156-165`).
- Undo — глобальный снапшот документа (`crates/engine/src/history.rs:8,106`).
- Каждая правка = incremental write + новый `RenderPool`
  (`crates/engine/src/session/editing.rs:332,392`); на 100k страниц ≈5 с.

## A. Журнал сырых `Edit` (тонкий сервер, движок как есть)

**Механизм.** Клиент шлёт `{opId, baseVersion, edit}`; сервер применяет
`Session::apply` в своём порядке, рассылает `applied {opId, version, editId}`.
Blob-параметры (`InsertPagesFrom`, `AddImage`, `ReplacePages`) — по ссылке на
загруженный объект. Клиент делает оптимистичный локальный `apply`, при
`reject`/`conflict` откатывается на снапшот из своего undo-стека.

- **Плюсы:** минимум новой семантики; всё, что умеет продукт, доступно
  автоматически; undo/redo и `Scope` уже есть; сервер — тонкий Rust-сервис
  с `engine`.
- **Минусы:** нужен serde на весь `Edit` (+ типы `annot/forms/organize`),
  включая деструктивные операции, которые нельзя пускать по сети; позиции
  (`page`, `index`, `path`) не переживают параллельную структурную правку;
  blob-поля раздувают сообщения; `Edit` — внутренний enum, его эволюция
  ломает wire-совместимость.
- **Где ломается:** два клиента добавляют аннотации на страницу 3, третий
  удаляет страницу 1 → все индексы съезжают; `DeleteAnnotation{page,index}`
  может удалить чужую аннотацию. `Batch` спасает только применение, не
  адресацию.
- **Оценка:** дёшево на старте, дорого в поддержке; высокий риск потери
  аннотаций — главный риск проекта.

## B. Нормализованные intent-операции + серверная трансляция (рекомендуется)

**Механизм.** Wire-формат — собственный набор операций в новом crate
`pdfcraft-collab-proto` (serde), а не `Edit`. У каждой операции есть:

- `opId` (клиентский UUID), `actorId`, `docId`, `baseVersion`, `epoch`;
- **класс**: `merge` (аннотация/комментарий/значение поля/статус) или
  `structural` (страницы, дерево закладок, структура полей);
- **адрес**: `annotation` → `/NM` + page-index + epoch; `field` → полное имя;
  `attachment` → ключ; `bookmark` → путь + epoch; `page` → индекс + epoch;
- **payload** без абсолютных путей/времени, blob — по `sha256`.

Сервер — единственный писатель. Для `structural` требует
`baseVersion == head` (иначе `reject{retryable:true}` + свежий снапшот);
применяет через `Edit` и увеличивает `epoch`. Для `merge` принимает на
любой базе, переводит адрес в актуальные `(page, index)`/`ObjRef` и
применяет поверх head; при смене `epoch` отвечает `reject{retryable:true}`.
Клиент применяет свои операции локально на COW-клоне (preview), серверные —
после `applied`; при reject откатывается к последнему подтверждённому
снапшоту.

- **Плюсы:**
  - адреса переживают сдвиги страниц (epoch + `/NM`/имя поля);
  - журнал компактный, пригоден для snapshot/replay;
  - allowlist классов и операций: redaction/sanitize/protect/flatten/XFA в
    сеть не попадают;
  - сервер проверяет роль и PDF-permissions до применения;
  - `Edit` остаётся внутренним и может меняться; wire-формат версионируется
    отдельно;
  - per-user undo = inverse-операции над текущим head, без откатов чужих
    правок;
  - один конверт годится всем пяти приложениям, различается только кодек
    операций.
- **Минусы:**
  - нужен слой трансляции wire→`Edit` (и обратно для локального preview);
  - нужен узкий API движка, отдающий стабильные ID страницы/аннотации, либо
    правило epoch (см. ниже);
  - две реализации одной семантики (клиент и сервер) надо держать в sync.
- **Как закрываем ID без большого рефакторинга:**
  1. Для аннотаций уже есть `/NM`; PdfCraft генерирует его UUID-подобным
     (`crates/engine/src/edit/run.rs:239-257`). Новые аннотации получают
     префикс `clientId`, сервер отвергает дубликаты и при необходимости
     назначает свой `annId`.
  2. Для страниц вводится `epoch`: любая структурная операция увеличивает
     его; merge-операции со старым epoch отклоняются retryable — клиент
     получает свежий список страниц. Внутри epoch индекс страницы стабилен.
  3. Для полей, вложений, закладок уже есть строковые/путевые адреса.
  4. Опционально (следующим шагом) — `Session::page_ref(page)` и
     `Session::annotation_ref(page, index)`, чтобы перейти с epoch на
     настоящие `ObjRef` без изменения wire-формата.
- **Оценка:** средний объём, низкий риск потери данных; лучше всего ложится
  на два класса действий из `TASK.md`.

## C. CRDT-first (аннотации и порядок страниц как CRDT, PDF как проекция)

**Механизм.** Аннотация — LWW-карта по UUID; страницы — список с
fractional-index/RGA; текст комментариев — sequence CRDT; сервер — релей и
хранилище состояния, commit — проекция CRDT в PDF.

- **Плюсы:** offline и конкурентные правки без блокировок; presence
  тривиален; нет «отклонённых» операций.
- **Минусы:**
  - PDF — объектный граф, а не дерево: закладки, `/Dest`, named destinations,
    `/PageLabels`, `/IRT` ссылаются на объекты; CRDT-порядок страниц придётся
    материализовать в `ObjRef` и переписывать все ссылки;
  - structural-операции всё равно нужно сериализовать (delete/move/insert
    меняют сам файл), т.е. получается гибрид, а не чистый CRDT;
  - нужен CRDT-стек на Rust (`yrs`/`automerge`), его лицензия допустима, но
    объём и WASM-бандл растут; в workspace сейчас нет async/CRDT зависимостей;
  - per-user undo в CRDT требует scope-undo (нет в движке);
  - commit становится недетерминированной проекцией; round-trip и подписи
    под угрозой;
  - тестировать сходимость без GUI сложнее, чем журнал операций.
- **Оценка:** высокий объём и высокий риск; не оправдан для 2–5 участников и
  рабочего процесса «комментарии + редкие структурные правки».

| Критерий (AGENDA §«Критерии оценки») | A | B | C |

| 2–5 участников, 100+ страниц | да, но позиции ломаются | да | да |
| Не шлёт документ на каждое нажатие | да (op) | да (op, компактнее) | да (delta) |
| Per-user undo | нет из коробки | да (inverse) | сложно |

| Разумный объём Rust/WASM | средний | средний | большой |

## Рекомендация: B

Причины, специфичные для PdfCraft:

1. **Главный риск проекта — потеря аннотаций при структурных сдвигах.**
   Вариант A адресует аннотации `(page, index)` и именно здесь ломается
   (`crates/annot/src/lib.rs:8-13`). B вводит epoch и `/NM`-адрес, поэтому
   комментарий не «переезжает» на чужую страницу.
2. **`Edit` нельзя отдавать в сеть.** Это внутренний enum на 106 вариантов с
   `Arc<Vec<u8>>` и деструктивными операциями; wire-формат должен быть
   отдельным и уже, с allowlist по ролям.
3. **Commit уже почти детерминирован.** Авторитетный сервер может держать
   `cos`/`Session`, применить журнал и один раз записать файл; `/ModDate`
   инжектируется (`Session::with_clock`). Для этого не нужен CRDT.
4. **CRDT не решает structural-часть.** PDF-файл всё равно переписывается
   сервером; CRDT добавил бы второй источник истины и риск round-trip.

## Позиция pdfcraft по 10 измерениям (для голосования)

| # | Измерение | Выбор | Обоснование для PdfCraft |
|---|---|---|---|
| 1 | Единица операции | **B** | нормализованная intent-операция; `Edit` — внутренний слой |
| 2 | Идентификаторы | **B** | `/NM` для аннотаций, имя поля, ключ вложения, путь закладки; `epoch` для страниц; `ObjRef` — как только движок отдаст API |
| 3 | Порядок и версии | **B** | один писатель, монотонный `version`; `baseVersion` для структурных, `epoch` для merge; `opId`-дедуп |
| 4 | Конфликты | **B** | structural — сериализация и reject при stale base; annotations/поля — LWW по свойству + merge ответов; без OT/CRDT |
| 5 | Снапшоты | **B** | база = PDF-байты + журнал; периодический snapshot incremental-записью; compaction сводит журнал в новую базу |
| 6 | Presence | **B** | отдельный эфемерный канал в том же WS, не журналируется; page+viewport+cursor+selection, троттлинг |
| 7 | Топология | **B** | один control plane (auth/lease/journal/commit) + per-app кодек операций; PDF-кодек — в отдельном crate |
| 8 | Auth и lease | **B** | JWT от кабинета в первом WS-сообщении, короткий `exp`, `role`+`doc`+`sid`; lease на документ; отзыв по `sid` |
| 9 | Commit | **B** | сервер собирает `.pdf` из авторитетного состояния; incremental, full только при delete/sanitize; `409` по etag внешнего изменения |
| 10 | Offline и undo | **B** | per-user inverse-журнал; offline-очередь только для merge-операций, structural — запрещены offline |

## Что не входит в это решение

- Конкретный wire-формат (protobuf/JSON/CBOR) — это RFC после ADR.
- Транспорт (WebSocket vs host-mediated `postMessage`) — RFC; у PdfCraft web
  сейчас нет WebSocket (`apps/pdfcraft-web/Cargo.toml`), native — нет
  async-рантайма.
- Шифрование/подписи в collab-сессии: рекомендуется v1 без них.
- Серверный snapshot-формат и TTL — ADR по измерению 5.
