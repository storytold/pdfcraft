- Проект: `pdfcraft`
- Upstream: `https://github.com/storytold/pdfcraft`
- Коммит: `f42fda734243b66f54db87923d7c981d5221419e` (2026-11-06)
- Дата: 2026-11-06
- Автор: `pdfcraft/envoy`

## 0. Краткий вывод

PDF в PdfCraft — не дерево текста, а **ленивый граф COS-объектов с
copy-on-write оверлеем**. «Модель» — это сам файл; правка — это `Edit` над
клоном `Document`, после которой движок делает incremental-запись и заново
поднимает view. Отсюда три главных факта для протокола:

1. **Стабильного ID в публичном API нет.** `DocInfo` отдаёт страницы как
   0-based индексы (`PageInfo`), аннотации — как `(page, index)` в `/Annots`,
   закладки — как `Vec<usize>` путей. `ObjRef` (номер объекта PDF) существует
   внутри `cos`, но наружу через `engine` не выставлен. `/NM` у аннотаций есть,
   но по контракту **не уникален**, и это уже обрабатывается в automation.
2. **Undo — глобальный снапшот документа, а не команда.** Стек на документ,
   до 100 состояний; отмена восстанавливает целый `cos::Document` (дешёвый
   COW-клон). Per-user undo «из коробки» нет.
3. **Каждая правка уже стоит пересборки.** После `apply` движок пишет
   incremental-ревизию и создаёт новый `RenderPool`; на 100 000-страничном
   файле полная реинспекция ≈ 5 с. Это делает «операцию на каждое нажатие» с
   серверным применением дорогой и требует батчинга/скоупов.

Рекомендация (детали в `options.md`): **вариант B** — авторитетный серверный
журнал нормализованных операций со стабильными идентификаторами, где
аннотации/комментарии/значения полей сливаются, а структурные операции
страниц сериализуются сервером. Сырой `Edit` (вариант A) не годится как
wire-формат: он не сериализуем, содержит `Arc<Vec<u8>>` и адресует всё
позициями. Чистый CRDT (вариант C) не ложится на PDF-граф, `/Dest`,
`ObjRef` и incremental-запись.

## 2. Модель документа

- Корневой тип: `pdfcraft_cos::Document` (`crates/cos/src/document.rs:36-80`).
  Внутри — исходные байты (`Arc<Vec<u8>>`), xref, ленивые кеши и **оверлей
  правок**: `BTreeMap<u32, Slot>` + `next_num` (`document.rs:57-60`). Клон
  дешёвый: неизменённые данные общие, поэтому клон и есть снапшот
  (`document.rs:1-5`).
- Типизированного дерева нет: «PDF object graph *is* the model»
  (`docs/architecture.md:41-45`). Страничное дерево обходится на чтение
  (`crates/organize/src/lib.rs:103-140`, `crates/model`), но при структурной
  правке пересобирается в **плоский** `/Pages` (`organize/lib.rs:8-12,172-196`).
- Узлы, с которыми работает совместная работа:
  - **страницы** — leaf `/Type /Page`, ссылки `ObjRef`; наследуемые
    `Resources`, `MediaBox`, `CropBox`, `Rotate` при restructuring копируются
    на лист;
  - **аннотации/комментарии** — записи в `/Annots` страницы; ответы связаны
    `/IRT` (ссылкой на объект), а не `/NM`; группы — `/RT /Group`
    (`crates/annot/src/info.rs:20-25`, `crates/render/src/inspect/model.rs:304-330`);
  - **поля формы** — отдельное дерево `/AcroForm /Fields`, в API
    «плоский» список терминальных полей с полным именем `parent.child`
    (`crates/forms/src/lib.rs:149-172`);
  - **закладки** — outline-дерево, в API путь `Vec<usize>`
    (`crates/engine/src/bookmarks.rs:5-19`);
  - **ссылки** — Link-аннотации, адресуются `(page, index)`;
  - **слои** — OCG с `ObjRef`, видимость хранится в view-state и в
    `/OCProperties /D` только для печати (`crates/engine/src/layers.rs:8-38`);
  - **вложения** — name-tree, ключ — строка (`DeleteAttachment { key }`);
  - **структурное дерево доступности** — теги, адресуются `ObjRef` в
    `a11y`-правках (единственное место, где `ObjRef` уже в `Edit`).
- Стили/форматирование живут в content streams и appearance streams
  аннотаций/полей; отдельных «стилевых» узлов нет.
- **Стабильные ID?** Внутри `cos` — да, `ObjRef { num, generation }`
  (`crates/cos/src/object.rs:12-16`), и он сохраняется при incremental-записи.
  Но:
  - публичный `DocInfo` страниц не содержит `ObjRef`: только
    `width/height/label/crop/rotation` (`crates/render/src/inspect/model.rs:98-108`);
  - аннотация в `DocInfo` — `page`, `index`, `name` (`/NM`)
    (`render/src/inspect/model.rs:304-330`), без `ObjRef`;
  - `Session`/`Document` не отдают `cos::Document` наружу; `annot_ref` в
    `crates/annot/src/lookup.rs:110` — `pub(crate)`.
  То есть **слой collab обязан либо добавить узкий API движка для `ObjRef`/
  session-id, либо жить на позиционных индексах с проверкой версии**.

## 3. Команды и мутации

- Единственная точка правки: `Session::apply(DocId, Edit) -> Result<(), EditError>`
  (`crates/engine/src/session/editing.rs:22`). Правка выполняется на клоне
  (`editing.rs:75-100`), при ошибке применения или refresh — откат клона
  (`editing.rs:200-215`).
- `Edit` — один enum, **106 вариантов** на этом коммите (`crates/engine/src/edit.rs:21`;
  `crates/engine/README.md:63` всё ещё говорит «75» — документация отстала).
  Варианты покрывают страницы, закладки, аннотации, поля, контент, OCR,
  безопасность, теги, XFA, redaction, flatten и `Batch`.
- **Параметры не сериализуемы.** Ни `Edit`, ни `NewAnnotation`, ни типы
  `annot`/`organize`/`forms` не имеют `serde` (`grep Serialize` по этим
  крейтам пуст, `serde` не в их `Cargo.toml`). Часть вариантов несёт
  `Arc<Vec<u8>>` (вставка страниц из другого PDF, изображения, штампы,
  `ReplacePages`), т.е. wire-формат требует blob-ссылок.
- Реестр команд (`crates/engine/src/commands.rs:165`) — это UI-действия
  (меню, ⌘K, контрольный канал), а не мутации; на коммите **216** команд
  (документация: 184, `docs/architecture.md:89`). Таблица automation —
  **195** инструментов (`crates/automation/src/tools.rs:134`; документация:
  141). Инструменты дают JSON-схемы и маппятся на `Edit`, это ближайший
  существующий «сериализуемый командный слой», но он 1:1 повторяет
  позиционную адресацию и не является протоколом.
- `Edit::Batch { label, edits }` применяет несколько правок как один
  undo-шаг; `scope_of` сводит скоупы, и refresh происходит один раз
  (`crates/engine/src/history.rs:54-93`). Это единственный существующий
  механизм батчинга — полезен серверу на окно коммита.
- Права проверяются по PDF-permissions (`crates/engine/src/edit/run.rs:9-140`):
  `assemble`, `annotate`, `fill_forms`, `modify` и т.п. **Ролей
  owner/editor/commenter/viewer в движке нет** — их должен проверять сервер.

## 4. Undo/redo

- Стек — в `Editor` документа: `Vec<(Label, cos::Document, Keys, Scope)>`
  (`crates/engine/src/history.rs:106`), лимит `MAX_UNDO = 100`
  (`history.rs:8`). В снапшоте лежит **весь документ**, но благодаря COW
  клон дешёвый (`docs/architecture.md:45-48`).
- `undo`/`redo` заменяют текущий `cos` снапшотом и делают
  `refresh_scoped` (`crates/engine/src/session/editing.rs:258-300`).
- Стек **глобальный на документ**, не на пользователя. Отмена восстанавливает
  состояние целиком, а не «мою» правку; для collab это непригодно напрямую.
- `Scope` (`history.rs:17-33`) позволяет после правки не делать полную
  реинспекцию: `Comments`, `Form`, `Links`, `Content`, `Metadata`, `Full`.
  Это важный рычаг производительности для серверного применения.

## 5. Сериализация и round-trip

- Читает/пишет `crates/cos`: ленивый толерантный парсер с ремонтом xref,
  writer с incremental и full режимами (`crates/cos/src/writer.rs:1-12`).
- `write_incremental` дописывает изменённые объекты, xref и trailer с
  `/Prev`, **не меняя исходные байты** (`writer.rs:206`). `write_full`
  пишет только достижимое из trailer и **перенумеровывает объекты плотно**
  (`writer.rs:8-9,339,571`) — `ObjRef` после него меняются.
- После каждой успешной правки движок пишет incremental-ревизию и обновляет
  view из этих байтов: «что видно, то и сохранится»
  (`crates/engine/src/session/editing.rs:311-392`).
- Read→write без правок не меняет файл: `save_bytes` возвращает исходные
  байты, если документ не изменён (`crates/engine/src/session/save.rs:21-25`).
- Полный rewrite только там, где иначе нельзя: redaction, PDF/A, смена
  пароля/шифрования, Save As, удаление страниц (для неподписанных файлов
  `delete_pages` требует full save, `editing.rs:171-174`).
- **Что не моделируется и теряется:**
  - структурные правки копируют наследуемые атрибуты на листы и **уплощают**
    дерево `/Pages`; промежуточные узлы становятся недостижимы и уходят при
    full save (`organize/src/lib.rs:8-12,172-196`);
  - `delete_pages` освобождает объекты страниц и удаляет закладки/ссылки,
    ведущие на них; `/PageLabels` пересчитывает (`organize/lib.rs:269-294`,
    `organize/src/labels.rs:400-424`);
  - `move_pages`/`insert_blank_page` пересобирают `/Pages`, но **не
    пересчитывают `/PageLabels`** — метки остаются позиционными
    (`organize/lib.rs:521-534,601-620`; в `import.rs` упоминаний меток нет);
  - подписанные документы нельзя полностью переписывать: правка, требующая
    full rewrite, возвращает `SignedRewrite` (`editing.rs:176-182`);
  - зашифрованные документы: incremental save перешифровывает, full save
    нужен при смене шифрования (`save.rs:26-40`);
  - `XfaToStatic` необратимо убирает XFA-пакеты, оставляя статическую форму.
- Неизвестные ключи и объекты сохраняются: «unknown data survives a round trip
  because nothing is reconstructed that wasn't understood»
  (`crates/engine/README.md:39-45`).

## 6. Структурные правки и их цена

Адресация почти везде **позиционная**: страницы — `usize`, аннотации —
`(page, index)`, ссылки — `(page, index)`, закладки — `Vec<usize>`, added
content / text line / image — `index`. Исключения: имя поля формы, ключ
вложения, `ObjRef` у тегов доступности.

| Операция | Что ломается при конкурентной правке | Цена пересчёта |
|---|---|---|
| rotate страниц | индекс страницы; позиция безопасна только при `baseVersion == head` | дешёвая правка словаря, но полный refresh + incremental write |
| delete страниц | сдвиг всех последующих индексов; аннотации/закладки/ссылки на удалённую страницу; `/PageLabels`; для неподписанных — **full save** и смена `ObjRef` | полная реинспекция; full rewrite на коммите |
| move / insert / duplicate | сдвиг индексов; `/PageLabels` не пересчитывается; новые объекты получают номера локально (`doc.add`, `cos/document/objects.rs:786-800`) → коллизии при слиянии | полная реинспекция |
| replace / insert from file | те же сдвиги + blob на входе + конфликты имён полей (`FieldConflicts`) | импорт страниц + полная реинспекция |
| split / combine / extract | это **новый документ**, а не `Edit` (`Session::split/combine`, `session/files.rs:191-374`); в сессии их место — только commit-time | открытие/запись нового файла |
| аннотация: добавить/ответить | `(page, index)`; ответы `/IRT` ссылками; при удалении корня ветки удаляются и ответы (`annot::with_replies_and_popups`) | `Scope::Comments`: без полной инспекции, но incremental write + новый `RenderPool` |
| аннотация: текст/цвет/rect/status | LWW по свойству; конфликт «ответ + удаление» | то же |
| поля: значения | LWW по полному имени; скрипты/расчёты могут каскадно менять другие поля (`Scope::Form`) | до сотен мс на больших формах (см. §8) |
| структура полей | только структурной операцией; `DuplicateField` делит значение | полная реинспекция |
| закладки | путь `Vec<usize>` нестабилен при вставке/удалении соседей | полная реинспекция |
| слои | видимость — view-state, не `Edit`; структура OCG — `ObjRef` | новый `RenderPool` без записи файла |

## 7. Существующие хуки для collab

- `Session` — фасад с `DocId(u64)`, `dirty`, `generation`, `edit_notices`;
  событийной шины нет, UI опрашивает состояние покадрово.
- `Edit` + `apply` + undo — готовая семантика правки; сервер может
  использовать `engine` headless (он не зависит от egui, `crates/engine/README.md:3-5`).
- `automation` (195 инструментов) — headless-слой и JSON-схемы, пригодные для
  описания wire-операций, но не сам протокол.
- Web-host мост: `pdfcraft:ready|open|save|dirty|failed` через
  `craft-web-host` (`apps/pdfcraft-web/src/main.rs:120-160`). Сообщений
  `session`, `presence`, `commit` ещё нет.
- Наблюдение за файлом: native watcher `file_watch` (250 мс), при внешнем
  изменении — reload или уведомление (`crates/ui-egui/src/platform/file_watch.rs:1-9`).
  Это готовый детектор внешнего изменения для commit/409.
- Контрольный канал `--control` — loopback-канал для агентов
  (`docs/architecture.md:93-97`); к collab не относится.
- **Придётся добавить:** узкий API движка для стабильных ID (`ObjRef` страницы
  и аннотации или session-id), применение чужой операции без локального
  undo-стека, per-user inverse, журнал/версии, транспорт, presence, commit.
- **Ограничение WASM:** на wasm32 рендер-пул потоков не имеет
  (`crates/render/src/raster/pool.rs:261-283`: `threads = 0`, рендер в
  вызывающем потоке), а web-sys фичи WebSocket в `Cargo.toml` нет. Значит,
  транспорт в браузере — либо host-mediated через `postMessage` (уже есть
  мост), либо добавление `web-sys/WebSocket`; блокирующих вызовов быть не
  должно.

## 8. Производительность

- Рендер — CPU, vendored `hayro`, затем текстура в GPU; пул 2–7 потоков на
  native (`crates/engine/src/doc_state.rs:50-52`), 0 потоков на wasm.
- После **каждой** правки: incremental write и новый `RenderPool`
  (`crates/engine/src/session/editing.rs:332,392`); для `Scope::Comments`
  полная реинспекция пропускается, но запись и пул создаются всё равно.
- Измерено в upstream (synthetic, release, Linux):
  - файл 1 GiB открывается за 0.7 с, пик 1.0 GiB; пять правок — 8.5 с,
    пик 2.1 GiB (`docs/gaps.md:310-315`);
  - 100 000 страниц / 28 MB: открытие 5.5 с, 403 MiB; **каждая правка
    реинспектирует ≈ 5 с** (`docs/gaps.md:315-317`);
  - 9 156 страниц: инспекция ≈ 500 MiB (`docs/gaps.md:309`);
  - форма 3 129 полей / 190 расчётов / 6 страниц: медиана правки
    267–459 мс (`docs/form-performance.md:71-90,132-137`);
  - рендер одной synthetic-страницы ≈ 6–9 мс (`docs/form-performance.md:140`).
- Типичный документ: showcase 13 страниц (README). Web-сборка ~13 МБ,
  ~5 МБ gzip (`INTEGRATION.md` проекта).
- Практический вывод: сервер не должен применять каждую аннотацию отдельным
  `Session::apply` на большом файле (≈5 с на правку). Нужен либо батч
  (`Edit::Batch`, один refresh), либо новый headless-путь применения без
  пересборки view, либо `Scope`-only применение.

## 9. Три варианта протокола (кратко)

| Вариант | Механизм | Плюсы | Минусы | Риск |
|---|---|---|---|---|
| A | журнал сырых `Edit`, сервер применяет как есть | минимум новой семантики, undo/поведение движка бесплатно | `Edit` не serde, blob-параметры, позиционная адресация, деструктивные правки в одном enum | средний |
| B | нормализованные intent-операции со стабильными ID; аннотации/поля сливаются, структура сериализуется сервером | адресация переживает сдвиги, компактный журнал, роли и идемпотентность на сервере | нужен слой трансляции и узкий API движка для ID | низкий |
| C | CRDT на аннотациях и порядке страниц, сервер-ретранслятор + проекция в PDF | offline/async без раунд-трипа | конфликт с `ObjRef`, `/Dest`, закладками и incremental save; тяжёлый стек | высокий |

Рекомендация и обоснование — в `options.md`.

## 10. Риски и открытые вопросы

1. **ID без API движка.** Публично доступны только индексы, `/NM` (не
   уникален) и имена полей. Нужен либо узкий API (`page_ref`, `annot_ref`,
   session-id), либо правило «структурная эпоха»: структурные операции
   сериализуются и требуют `head`, а merge-операции несут epoch и при его
   смене отклоняются retryable.
2. **Две цены правки.** Локальная оптимистичная правка + серверное
   применение = две пересборки. Оптимистичный preview должен жить на клоне
   без incremental-записи; иначе UI будет платить дважды.
3. **Per-user undo.** Снапшот-стек движка глобальный. Нужны inverse-операции
   (компенсации) от сервера, иначе undo одного пользователя откатит чужие
   правки.
4. **Деструктивные операции.** `Edit` содержит redaction, sanitize, protect,
   flatten, XFA→static. Для collab-сессии нужен allowlist по роли; сервер не
   должен принимать их по сети.
5. **Подписи и шифрование.** На подписанном файле удаление страниц требует
   full rewrite и движок вернёт `SignedRewrite`. Для v1 разумно запретить
   collab на подписанных и зашифрованных PDF (или требовать явного
   owner-unlock на сервере, что противоречит «не хранить секреты»).
6. **Метки страниц.** `move/insert` не пересчитывают `/PageLabels`; при
   совместной перестановке это станет заметным расхождением номеров.
7. **Детерминизм commit.** `/ModDate` и `/NM` генерируются; для
   идемпотентности нужен `opId`-дедуп и инъекция часов на сервере
   (`Session::with_clock`, `session.rs:29-34`).
8. **Размер снапшота.** Снапшот = байты рабочего файла (исходник + одна
   ревизия), не модель. Для 1 GiB файла это дорого; нужна политика
   снапшотов/compaction на сервере.
9. **Presence и рендер.** Курсор/выделение других участников надо рисовать
   поверх страницы; на wasm рендер в UI-потоке, поэтому частые remote-правки
   могут ронять кадры — нужен троттлинг и приоритеты.
10. **Нет публичного события.** `Session` не имеет подписки; клиенту нужен
    либо колбэк движка, либо собственный слой diff после `apply`.

## 11. Что проверено и чего не проверено

- Проверено по коду: всё, что помечено `file:line` выше.
- Не проверено запуском: в окружении Phase 0 нет `cargo`/`rustc`, сборка не
  выполнялась; числа производительности взяты из `docs/gaps.md` и
  `docs/form-performance.md` (upstream, 2026-10). Собственных замеров нет.
- Не проверено на реальных документах кабинета: корпус PDF не предоставлен,
  размеры/структура типичных файлов ЛЗМКМ неизвестны.
