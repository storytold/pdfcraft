# pdfcraft-platform

Layer L7 holds operating-system services that both the desktop app (`pdfcraft-ui-egui`) and the automation tools (`pdfcraft-automation`) need. Those two crates sit on the same layer and can't depend on each other, so a helper they share lives here instead of being copied into each (`xtask/src/layers.rs` allows both edges). It has no UI dependencies; macOS filesystem calls use the safe `rustix` and `exacl` wrappers.

`staging` creates the temporary file an atomic save writes before renaming it over the target. The file is opened with `create_new`, so anything already at the name (a file, a hard link, a symbolic link even when dangling, a folder) is skipped and never written through. On Windows a folder at the name fails with "access denied" rather than "already exists", and is skipped only when something is actually there. Names carry an unpredictable 64-bit suffix from `staging_suffixes` (the standard library's keyed hash, currently SipHash-1-3, keyed from the operating system's random source), which stops a name being planted in advance but is not a CSPRNG; fixed suffixes are only for tests. At most 16 names are tried, and then the save is refused. The target's name is cut to 128 bytes on a character boundary so the staging name fits every system's limit. Each caller keeps its own name form (`.{name}.{suffix}.pdfcraft-tmp` for automation, `.{name}.pdfcraft-{suffix}.tmp` for the desktop save). Writing, closing the file before the rename, renaming and removing the staging file on failure stay with the caller.

Synthetic tests pin both name forms, the 128-byte cut, the attempt limit and refusal when no name is left. The planted-file, link, folder and failed-rename tests stay with each caller, where they exercise the whole save.

On macOS, `write_atomically_with` copies the existing regular destination's accessible extended attributes to the open staging file after writing the data and before flushing and renaming. Finder tags, comments, binary values and empty attributes therefore survive both incremental and full saves (#2658). Save As retains attributes of an existing destination; a new destination does not inherit metadata from the source PDF. Missing files and filesystems without xattr support keep working. The metadata read does not follow the destination's symlink or block on a FIFO. macOS manages the new file's `com.apple.provenance`; it is not copied. Kernel-hidden compression attributes are not requested.

Attribute copying is bounded: 64 KiB of names, 1024 attributes, 16 MiB per value and 64 MiB total. Each value must fill the initially queried size and retain that size in a second query after reading: a resource fork may return a partial prefix on growth rather than an error. A read/copy error or exceeded bound returns an error suggesting Save As; the original bytes and metadata stay intact and staging cleanup is attempted. Flush errors retain the same guarantee. Tests cover exact metadata before flush and after repeated saves, empty/binary values, oversized resource forks, a simulated partial read of a growing fork and symlink isolation. Automation covers incremental/full saves, Save As and retaining an unsaved edit after metadata refusal. The staging writer also retains Unix permissions, the Windows hidden and system attributes (the staging file is created with them, so a hidden file is never published visible and a plain one never hidden, #4593) and, where supported, Windows/macOS creation dates; attribute copying runs before the creation date is restored. Hard-link identity is not preserved.


On macOS, replacing an existing direct regular file also preserves its native extended ACL (#2658).
One held, no-follow destination descriptor supplies ACLs, xattrs, mode, group and creation time.
The staging file starts owner-only; its mode is broadened only after the native ACL has been installed, without reconstructing entries or resolving names.
If the new staging file inherits any ACL entries, replacement is refused before PDF bytes are written, because tightening an ACL cannot revoke a read handle opened earlier.
Any deny-delete entry in the captured source ACL conservatively refuses replacement before that ACL or PDF bytes reach staging, regardless of principal; otherwise a failed rename could leave undeletable staged PDF data.
The caller validates an entry view of the exact native snapshot that is then applied, without rereading or reconstructing the ACL.
Unsupported ACL retrieval/application and mode-setting failures also refuse replacement and retain the original file and unsaved edits.
Cleanup is attempted on failure; directory permissions or an inherited delete denial may prevent removal of an empty pre-payload staging file.
Save As to an existing file preserves that destination's ACL; a fresh name follows the chosen folder's usual inheritance and does not copy the input document's ACL.
Observed destination identity or metadata changes refuse publication, but this is not an atomic lock against hostile concurrent pathname or ACL changes.
The established symlink replacement behavior is retained without copying the referent's ACL or xattrs.
Windows DACL preservation and hard-link identity remain outside this behavior.
See `vendor/exacl/README-PDFCRAFT.md` for the exact MIT source and temporary safe opaque-copy facade.
