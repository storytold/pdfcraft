Git Remotes, PR Lifecycle & Conflict Resolution

A compressed field guide for open-source contributors navigating forks, pushing commits to active pull requests, syncing upstream updates, and resolving merge conflicts cleanly.

1. Identifying Your Directory & Remotes

A Git repository clone on your machine is a self-contained local database connected to named remote servers:

Entity What it is Your Actual URL
This Directory Your local working copy on your laptop/PC. /media/saifallah/.../pdfcraft
origin Your personal fork on GitHub (read & write). https://github.com/Saifallah-star/pdfcraft-storytold.git
upstream The original repository (read/pull only). https://github.com/PDFCraftTool/pdfcraft.git 
# Check remotes at any time:
git remote -v

# Check current branch and what remote tracking branch it follows:
git status
git branch -vv

2. How to Add Commits to an Existing Pull Request

A Pull Request is not an uploaded file snapshot. It is a live comparison between your branch on GitHub (origin/<branch>) and the project's target branch (upstream/main).

Key Rule

Any commit you push to your branch on GitHub is automatically appended to the open Pull Request. You never need to open a new PR to push fixes or address reviewer comments.

# 1. Ensure you are on the feature branch
git checkout feat/tear-off-window-viewports-issue-5348

# 2. Make your code changes, then stage the modified files
git add path/to/changed_file.rs

# 3. Create a descriptive commit
git commit -m "fix(viewport): handle window close event gracefully"

# 4. Push to your fork (origin)
git push origin feat/tear-off-window-viewports-issue-5348

# -> GitHub updates the PR instantly!

3. Syncing Others' Work / Merging Upstream into your PR

When the original repository moves forward, you need to pull in new commits to keep your branch up-to-date and prevent regressions.

Standard Merge (Simplest)

Creates a merge commit combining the two branch histories. Safe and preserves full timeline context.

git fetch upstream main
git checkout feat/your-branch
git merge upstream/main
git push origin feat/your-branch

Rebase (Linear History)

Unwinds your commits, applies latest upstream commits, then replays your commits on top.

git fetch upstream main
git checkout feat/your-branch
git rebase upstream/main
git push origin feat/your-branch --force-with-lease

4. Resolving Conflicts: The Step-by-Step Loop

A conflict happens when Git cannot automatically merge changes because two branches edited the exact same lines.

Anatomy of Conflict Markers

src/example.rs
<<<<<<< HEAD (Current branch: your changes)
let default_padding = 16.0;
======= (Divider)
let default_padding = 12.0;
>>>>>>> upstream/main (Incoming branch: upstream changes)

The 5-Step Resolution Loop

  1. Find conflicted files: Run git status. Look for files under "both modified".
  2. Open and decide: In your editor, examine the conflicting code. Decide what the final code should be (keep yours, keep theirs, or combine both).
  3. Delete the markers: Delete <<<<<<<, =======, and >>>>>>> completely.
  4. Verify: Run tests or build checks (e.g., cargo check) to make sure there are no syntax errors.
  5. Stage and finish: 
    git add src/example.rs

# If you were merging:
git commit -m "Merge upstream/main and resolve padding conflict"
git push origin <branch>

# If you were rebasing:
git rebase --continue
git push origin <branch> --force-with-lease
Emergency Panic Button

If you make a mistake while resolving conflicts and want to start over cleanly without losing your original commits:

# To abort a merge:
git merge --abort

# To abort a rebase:
git rebase --abort
